1. From a design to DDL

Data definition language (DDL) creates or changes database objects. Chapter 10 decided what the structure means; Chapter 11 expresses that reviewed plan in MySQL.

Analogy: construction follows the blueprint

A table definition is a construction specification. Column types describe materials, a primary key gives every unit an identity, and foreign keys connect one part of the structure to another. Changing the plan while pouring concrete is expensive, so review first and build second.

Create

Build an object

CREATE DATABASE, CREATE TABLE, and CREATE INDEX add structure.

Alter

Change an object

ALTER TABLE can add, modify, or remove columns and constraints.

Remove

Empty or destroy

TRUNCATE removes all rows; DROP removes the object. Both require deliberate confirmation.

Non-negotiable course boundary

The publisher's ap schema is read-only. Run Chapter 11 DDL only in your personal ap_sandbox, and only when Canvas authorizes the step. If that sandbox is missing or you are connected to a shared server, stop and ask rather than creating a substitute.

DDL is not ordinary transaction practice

Most MySQL DDL statements cause an implicit commit. MySQL 8.4 supports atomic DDL for metadata consistency during failure, but that does not mean your later ROLLBACK can undo a completed CREATE, ALTER, TRUNCATE, or DROP.

2. Create, select, and drop databases carefully

In MySQL, database and schema are commonly used for the same named container. Creating the container does not automatically select it for unqualified table names.

Personal local server only · when Canvas directs 
CREATE DATABASE IF NOT EXISTS ap_sandbox
    CHARACTER SET utf8mb4
    COLLATE utf8mb4_0900_ai_ci;

USE ap_sandbox;

SELECT DATABASE() AS current_database;
  1. Confirm the connection and server named in Canvas.
  2. Create ap_sandbox only if the assignment tells you to create it.
  3. Use USE ap_sandbox or fully qualify every object as ap_sandbox.table_name.
  4. Run SELECT DATABASE() before DDL and verify the result.

Understand DROP DATABASE without practicing it on course data

DROP DATABASE removes the schema and its objects. The syntax below is shown to complete the chapter vocabulary; do not run it against ap, ap_sandbox, ShopFlow, or an assigned server.

Syntax illustration only 
DROP DATABASE your_disposable_schema;

3. Create tables from meaning, types, and nullability

A column definition combines a name, data type, and rules such as NOT NULL or DEFAULT. Keep names lowercase and descriptive so scripts behave consistently across operating systems.

ap_sandbox · parent table 
CREATE TABLE ap_sandbox.terms_work (
    terms_id INT PRIMARY KEY,
    terms_description VARCHAR(50) NOT NULL,
    terms_due_days SMALLINT UNSIGNED NOT NULL,
    CONSTRAINT chk_terms_work_due_days
        CHECK (terms_due_days >= 0)
) ENGINE = InnoDB;
What each part of the definition communicates
Definition part Meaning Beginner question
SMALLINT UNSIGNED A nonnegative whole-number range Is the range sufficient for allowed due days?
VARCHAR(50) Up to 50 characters of variable-length text Is the value text, and is the limit justified?
NOT NULL A value is required Can the business fact genuinely be unknown?
DEFAULT A value supplied when an insert omits the column Is that default true, or would it invent a fact?

Two MySQL 8.4 details

  • AUTO_INCREMENT creates identifiers, not gap-free business sequence numbers. Gaps are normal.
  • A CHECK condition accepts TRUE or UNKNOWN. Pair a range check with NOT NULL when the value is required.

4. Use constraints as guardrails

Constraints make design rules executable. Name them so error messages, inspection, and later changes can refer to a meaningful rule.

Analogy: guardrails do different jobs

A primary key is an identity checkpoint, a unique constraint prevents duplicate business identifiers, a foreign key blocks orphan references, and a check constraint keeps values inside an allowed rule. One guardrail cannot replace the others.

ap_sandbox · child table with named constraints 
CREATE TABLE ap_sandbox.vendors_work (
    vendor_id INT AUTO_INCREMENT PRIMARY KEY,
    vendor_name VARCHAR(50) NOT NULL,
    default_terms_id INT NOT NULL,
    CONSTRAINT fk_vendors_work_terms
        FOREIGN KEY (default_terms_id)
        REFERENCES ap_sandbox.terms_work (terms_id)
) ENGINE = InnoDB;
Constraint questions to ask before running DDL
Constraint Question it answers Important MySQL detail
Primary keyHow is each row identified?It is unique and non-null and creates an index.
UniqueWhich other value or combination may not repeat?A nullable unique key can permit multiple NULL values.
Foreign keyWhich parent row must exist?Child and parent key types must be compatible.
CheckWhich row-level condition must not be false?Use NOT NULL separately when unknown is not allowed.

Write a real table-level foreign key

Do not rely on an inline column phrase such as vendor_id INT REFERENCES vendors_work(vendor_id). In MySQL, define the relationship with a separate FOREIGN KEY (...) REFERENCES ... constraint as shown above.

Constraint gate: what blocks the row?

Choose a proposed row to identify the first relevant guardrail.

Foreign-key guardrail

A vendor cannot reference a terms_id that is absent from terms_work.

Check-constraint guardrail

A named CHECK (invoice_total >= 0) rejects a negative amount.

Unique-constraint guardrail

A composite unique constraint on vendor and invoice number can prevent that business identifier from repeating for the same vendor.

5. Build a dependency-safe creation script

Create a referenced parent before the child that depends on it. For removal, reverse the order. This makes the script readable and avoids treating integrity checks as obstacles to bypass.

Analogy: install the shelf before the hanging basket

A child table's foreign key hangs from a parent key. Build the parent support first, attach the child next, and dismantle the child before removing the parent.

ap_sandbox · simplified creation order 
-- 1. Confirm the target.
SELECT DATABASE() AS current_database;

-- 2. Create the independent parent first.
CREATE TABLE ap_sandbox.terms_work (
    terms_id INT PRIMARY KEY,
    terms_description VARCHAR(50) NOT NULL,
    terms_due_days SMALLINT UNSIGNED NOT NULL,
    CONSTRAINT chk_terms_work_due_days
        CHECK (terms_due_days >= 0)
) ENGINE = InnoDB;

-- 3. Create the child after its parent exists.
CREATE TABLE ap_sandbox.vendors_work (
    vendor_id INT AUTO_INCREMENT PRIMARY KEY,
    vendor_name VARCHAR(50) NOT NULL,
    default_terms_id INT NOT NULL,
    CONSTRAINT fk_vendors_work_terms
        FOREIGN KEY (default_terms_id)
        REFERENCES ap_sandbox.terms_work (terms_id)
) ENGINE = InnoDB;

-- 4. Create the next child after vendors_work exists.
CREATE TABLE ap_sandbox.invoices_work (
    invoice_id INT AUTO_INCREMENT PRIMARY KEY,
    vendor_id INT NOT NULL,
    invoice_number VARCHAR(50) NOT NULL,
    invoice_date DATE NOT NULL,
    invoice_total DECIMAL(10,2) NOT NULL,
    CONSTRAINT uq_invoices_work_vendor_number
        UNIQUE (vendor_id, invoice_number),
    CONSTRAINT chk_invoices_work_total
        CHECK (invoice_total >= 0),
    CONSTRAINT fk_invoices_work_vendor
        FOREIGN KEY (vendor_id)
        REFERENCES ap_sandbox.vendors_work (vendor_id)
) ENGINE = InnoDB;

-- 5. Inspect the definitions MySQL stored.
SHOW CREATE TABLE ap_sandbox.terms_work;
SHOW CREATE TABLE ap_sandbox.vendors_work;
SHOW CREATE TABLE ap_sandbox.invoices_work;

IF NOT EXISTS can make a script easier to rerun, but it does not compare an existing object with the intended definition. Use SHOW CREATE TABLE to inspect the real result.

Quick check: choose the safe creation order

vendors_work.default_terms_id references terms_work.terms_id. Which table should the script create first?

6. Alter, rename, truncate, and drop with a preview mindset

DDL changes structure immediately enough that a safe workflow must replace the “I can always roll it back” assumption.

  1. Confirm the connection, schema, and exact object name.
  2. Inspect the current definition with SHOW CREATE TABLE.
  3. Review dependent foreign keys, views, scripts, and application queries.
  4. Test the statement on a disposable or approved sandbox copy.
  5. Run one intended change, inspect the result, and record what changed.
ap_sandbox · permitted scratch-table example 
ALTER TABLE ap_sandbox.vendors_work
    ADD COLUMN vendor_phone VARCHAR(20) NULL;

SHOW CREATE TABLE ap_sandbox.vendors_work;
Constraint changes use the names stored by MySQL
Approved scratch-table goal ALTER TABLE form Check first
Add a named ruleADD CONSTRAINT constraint_name ...The rule is valid for every existing row.
Remove a foreign keyDROP FOREIGN KEY constraint_nameNo required relationship is being abandoned.
Remove a checkDROP CHECK constraint_nameAnother rule is not relying on the check.

Use SHOW CREATE TABLE to get the actual constraint names. Do not guess a generated name, and do not remove a guardrail merely to make invalid data load.

Statements that look similar but have different consequences
Statement Effect Safety fact
RENAME TABLEChanges the object's nameDependent code may still use the old name.
TRUNCATE TABLERemoves every row while keeping the table definitionIt causes an implicit commit, does not fire delete triggers, and may be blocked by referencing foreign keys.
DROP TABLERemoves the table definition and its dataIt is destructive DDL, not a reversible row delete.

Do not “solve” relationship errors by disabling protection

Fix dependency order, key definitions, and data quality. Temporarily bypassing referential checks can admit orphan rows, and turning checks back on does not retroactively validate those rows.

7. Create useful indexes, not every possible index

An index can reduce lookup work for the query patterns it matches, but it consumes space and must be maintained during inserts, updates, and deletes.

Analogy: the back-of-book index

A reader can jump from “vendor” to the right pages without scanning the entire book. But an index entry for every unimportant word would make the index larger than the lesson. Select entries that support real questions.

ap_sandbox · measured query candidate 
CREATE INDEX idx_invoices_work_vendor_date
    ON ap_sandbox.invoices_work
       (vendor_id, invoice_date);

SHOW INDEX
FROM ap_sandbox.invoices_work;
Removal syntax · run only when the scratch exercise directs 
DROP INDEX idx_invoices_work_vendor_date
    ON ap_sandbox.invoices_work;

MySQL uses the index name and table name when dropping an index. Inspect first so you do not remove an index required by a constraint or still needed by a real access pattern.

What a composite index on (vendor_id, invoice_date) can support
Filter pattern Leftmost-prefix fit Reason
vendor_id = ?YesIt uses the first index column.
vendor_id = ? AND invoice_date >= ?YesIt uses the first column, then a range on the second.
invoice_date = ? aloneNot a direct leftmost-prefix lookupThe first index column is missing.

Know which indexes already exist

A primary key and each unique constraint create indexes. InnoDB also requires supporting indexes for foreign keys and can create a child-side index when one is missing. Inspect before adding an overlapping index, and use EXPLAIN with a real query.

8. Use Workbench—and verify text, character rules, and engines

Workbench can edit columns, indexes, and foreign keys through panels, but the server executes SQL. Review the generated statement and inspect the stored definition afterward.

Character set

Which characters can be stored?

Use utf8mb4 for full Unicode support in new course objects.

Collation

How are strings compared and sorted?

utf8mb4_0900_ai_ci is accent-insensitive and case-insensitive. Choose deliberately when those distinctions matter.

Storage engine

What machinery stores the table?

InnoDB is MySQL 8.4's default and supports transactions, row-level locking, and foreign keys.

Analogy: alphabet, dictionary order, and engine

The character set is the alphabet available to write names. The collation is the dictionary rule for deciding whether letters compare alike and where they sort. The storage engine is the machinery beneath the cabinet that manages how records are stored and protected.

  1. Open the table editor for the approved ap_sandbox object.
  2. Change only the requested column, index, or foreign-key definition.
  3. Review the SQL preview before applying it.
  4. Apply the change only when the target and statement are correct.
  5. Run SHOW CREATE TABLE and SHOW INDEX to verify what MySQL stored.

Why not type only utf8?

In MySQL 8.4, utf8 is a deprecated alias for the three-byte utf8mb3 character set. Spell utf8mb4 explicitly so supplementary Unicode characters are supported and the intended behavior remains clear.

9. Wrap-up and practice

The core habit: confirm, build, inspect

Confirm the target schema, build parents before children, and inspect the stored definition. DDL is safest when each statement implements one reviewed design decision.

Chapter 11 checklist

  • I can create or select only the personal schema authorized in Canvas.
  • I can create tables in dependency order with suitable types and nullability.
  • I can explain primary, unique, foreign-key, and check constraints.
  • I can use named table-level foreign-key constraints.
  • I understand why DDL and TRUNCATE are not undone by a later rollback.
  • I can choose an index from a real access pattern and explain its leftmost prefix.
  • I can distinguish character set, collation, and storage engine.
  • I verify Workbench changes with SHOW CREATE TABLE.

Final quick check

Workbench reports that an approved scratch-table change succeeded. What is the best next step?

Transfer the skill, not the schema

ShopFlow also needs thoughtful tables, constraints, character rules, and indexes, but it remains a separate project schema. Do not copy AP objects into ShopFlow or use the canonical ap database as a DDL practice area.
