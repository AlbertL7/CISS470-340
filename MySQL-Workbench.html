🔗 Part 3: Creating Relationships

Now we'll connect the tables. We'll create 18 relationships total.

IMPORTANT: The foreign-key columns already exist in this model. Use Workbench's Place a Relationship Using Existing Columns tool, then verify the mapping in the child table's Foreign Keys tab. This avoids accidentally creating duplicate columns.

  • Map the existing foreign-key column in the child table
  • Reference the primary key in the parent table
  • Confirm both columns have compatible data types
  • Review optionality separately from identifying status

Workbench creates the constraint only after you confirm the mapping. Always inspect the result rather than assuming the tool chose the intended column.

Understanding Relationship Lines in MySQL Workbench:

MySQL Workbench has TWO types of relationship tools:

  • ━━━ Solid Line (Identifying Relationship) — use only when the parent's foreign key is part of the child's primary key.
    • This is about key structure, not merely whether the relationship is required.
    • None of this lab's 12 tables use that pattern because every child has its own surrogate primary key.
  • ┅┅┅ Dashed Line (Non-Identifying Relationship) — the foreign key is outside the child's primary key.
    • Use this for all 18 relationships in this lab.
    • A dashed relationship can still be required; nullability controls optionality.

How to Create a Relationship:

  1. Select Place a Relationship Using Existing Columns. Because the child foreign keys are outside their primary keys, the finished connectors should be dashed.
  2. Click the CHILD/many table first — the table that already contains the foreign-key column.
  3. Click the PARENT/referenced table second — the table with the referenced primary key.
  4. Map the listed child column to the listed parent column and verify the Foreign Keys tab.

Visual Guide to Tools:

In the MySQL Workbench toolbar, you'll see these relationship tools:

  • ━━━┤ = 1:1 Identifying (solid line, one-to-one)
  • ┅┅┅┤ = 1:1 Non-Identifying (dashed line, one-to-one)
  • ━━━< = 1:n Identifying (solid line, one-to-many)
  • ┅┅┅< = 1:n Non-Identifying (dashed line, one-to-many)

For this model: choose the dashed 1:n existing-columns workflow for every relationship because each child table has a separate surrogate primary key.

Troubleshooting Relationships:

  • If you can't find the right tool:
    • The tools are in the left vertical toolbar
    • Hover over each icon to see tooltips
    • Solid line = identifying; dashed line = non-identifying
    • This lab uses dashed, existing-column relationships throughout
    • Workbench's documented 1:n sequence is child/many first, then parent/referenced
  • If the relationship arrow is going the wrong way:
    • You clicked the tables in the wrong order
    • Delete the relationship (select it and press Delete key)
    • Try again, clicking the child table first and the parent table second
  • If you see a dialog asking about columns:
    • This happens when column names don't match exactly
    • Select the correct columns from the dropdowns
    • For example: address_id → ship_address_id
  • If the relationship won't create:
    • Check that both columns have the same data type (both INT)
    • Make sure the parent table has a primary key
    • Verify the column exists in both tables

🧠 What's a Junction Table?

A junction table is basically a "relationship table" that connects two other tables when both sides can have many of each other.

It's like the middleman in a complicated relationship status.

💬 Think of it like:

"It's complicated — we need a table for that."

🎵 Example: Playlists and Songs

You have:

  • A Playlists table
  • A Songs table

One playlist can have many songs, but one song can also appear in many playlists.

That's a many-to-many relationship.

You can't just add a single "playlist_id" inside the Songs table — because each song could belong to lots of playlists.

So you make a junction table called, for example, Playlist_Songs.

playlist_id | song_id -------------|---------- 1 | 10 1 | 14 2 | 10 2 | 18

Now:

  • Playlist #1 has songs #10 and #14
  • Playlist #2 has songs #10 and #18
  • Song #10 is in both playlists

🧩 How It Works

That junction table just has two foreign keys — one from each main table:

  • One connects to Playlists.playlist_id
  • One connects to Songs.song_id

Together, they show the connection between the two.

💡 Why It's Important

  • It keeps your database organized and normalized
  • You don't repeat data all over the place
  • You can easily look up connections between things
  • You can add extra columns like "date_added" or "rating" if you want more info about the relationship itself

🛒 Real Examples You'll See

Relationship Junction Table
Orders ↔ Products Order_Items

🔑 TL;DR

A junction table:

  • Lives between two tables
  • Handles many-to-many connections
  • Has two foreign keys
  • Keeps everything clean, flexible, and easy to query

Basically — it's the "matchmaker" of your database 💘

Understanding the Design

Why Junction Tables?

Junction tables (Order_Items, Shopping_Cart, Wishlists) solve many-to-many relationships:

  • Orders ↔ Products: An order contains many products; a product appears in many orders
  • Customers ↔ Products (Cart): Customers can cart many products; products can be in many carts
  • Customers ↔ Products (Wishlist): Customers can wish for many products; products can be wished by many
