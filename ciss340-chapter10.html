1. Design is the blueprint

Database design decides what each row means, where each fact belongs, and which rules keep related facts trustworthy. SQL construction comes after those decisions.

Analogy: blueprint first, construction second

An architect decides where rooms belong and how people move between them before a builder pours concrete. Chapter 10 is the blueprint: entities, columns, keys, relationships, and normalization. Chapter 11 is the construction work that turns that plan into MySQL objects.

Meaning

What does one row represent?

Every table needs one stable grain statement that all its columns can honor.

Structure

What depends on what?

Functional dependencies reveal which facts belong together and which facts are being repeated.

Rules

How may rows relate?

Keys, cardinality, and optionality translate business rules into a design we can test.

2. Start with grain and data elements

Grain is the promise a table makes about one row. Write the promise before naming columns: One row represents ...

Analogy: label the storage box

If a box is labeled “one invoice line,” it may hold a line amount and account code. Vendor phone numbers do not belong in that box; they describe a vendor and would be copied into every line. A clear label prevents mixed meanings.

Useful AP grain statements
Table One row represents Examples of facts at that grain
vendors One vendor Name, address, phone, default terms
invoices One invoice from one vendor Invoice number, dates, totals, terms
invoice_line_items One account-coded line on one invoice Sequence, account, line amount, description

Find dependencies, not just nouns

A functional dependency says that one value determines another. These plain-language arrows help locate facts:

  • vendor_id → vendor details
  • terms_id → terms description and allowed days
  • invoice_id → that invoice's vendor, number, dates, and totals
  • account_number → general-ledger account description

Dependencies describe the business meaning. They are not claims that an ID causes another fact; they say the ID identifies the one fact that belongs with it.

Quick check: state the grain

A flat export repeats the same invoice once for every account-coded line. What does one export row represent?

3. Turn meanings into tables, keys, and relationships

After identifying grain and dependencies, group facts into tables. Then choose keys that identify rows and foreign keys that connect related grains.

Five-table AP design path used in Week 3 practice
Table Primary key Important foreign-key direction
terms terms_id Referenced by vendors and invoices
vendors vendor_id default_terms_id points to terms
invoices invoice_id vendor_id points to vendors; terms_id points to terms
general_ledger_accounts account_number Referenced by invoice line items
invoice_line_items invoice_id plus invoice_sequence Points to invoices and general-ledger accounts

Analogy: an address book, not repeated sticky notes

Store a vendor's details once in the address book. Each invoice carries the vendor's identifier, like a contact shortcut, instead of another copy of the phone number and address.

Cardinality and optionality are separate ideas

A crow's-foot marker means many. A circle means zero is permitted; a bar means one. Read the symbols at both ends rather than treating the crow's foot alone as a complete “zero-to-many” rule.

The foreign key normally appears on the child/many side. For example, many invoices may belong to one vendor, so invoices.vendor_id refers to vendors.vendor_id.

Many-to-many needs a bridge

If one invoice can use many accounts and one account can appear on many invoices, place the relationship facts in invoice_line_items. The bridge also stores facts such as line amount and sequence that belong to the pairing.

4. First normal form: one consistent row shape

First normal form (1NF) gives each table a consistent row grain, removes repeating column groups, and keeps each stored value single-valued for the domain the course has defined.

Analogy: one item per labeled slot

A form with columns named account_1, account_2, and account_3 is like a cabinet with only three numbered slots. The fourth account has nowhere to go. A line-item table gives every account-coded line its own row, so the design can grow without adding another column.

Spotting first-normal-form problems
Problem pattern Why it hurts Design response
Numbered repeating columns A fixed number of slots limits future rows and complicates queries. Move the repeating fact to rows in a related table.
Comma-separated account codes Individual codes are difficult to validate, join, or summarize. Store one account-coded line per row.
Mixed invoice and line facts Invoice facts repeat for every line, creating update anomalies. Separate invoice grain from invoice-line grain.

“Atomic” depends on the question

A full street address might be sufficient for display, but city and postal code must be separate if the business filters or validates them independently. Define useful domains from requirements instead of splitting every value without purpose.

5. Second and third normal forms: put every fact in its proper home

After 1NF, ask which key determines each non-key fact. The practical CISS 340 target is a defensible design through third normal form.

Second normal form

Depend on the whole key

2NF matters when a candidate key has more than one column. A non-key fact must depend on the full key, not just part of it.

Third normal form

Depend on the key, not another fact

In 3NF, a non-key fact should not determine another non-key fact. Vendor details therefore belong with the vendor, not in every invoice.

Apply the tests to invoice lines

With the composite key (invoice_id, invoice_sequence), invoice date depends only on invoice_id, so it belongs in invoices, not invoice_line_items. An account description depends on account_number, so it belongs in general_ledger_accounts.

A surrogate key is not a normalization shortcut

Adding an auto-generated ID can identify a row, but it does not remove partial or transitive dependencies. Continue checking what the business facts depend on.

6. Choose index candidates—and denormalize only with evidence

Design identifies likely access paths, but it should not create an index for every column. Start with keys and frequent, selective filters or joins, then validate with real queries and EXPLAIN.

Analogy: a book index has a maintenance cost

A good index helps a reader jump to the right page. An index containing every word would be bulky and expensive to maintain. Database indexes trade storage and write work for faster access to particular patterns.

Beginner index decisions
Observed access pattern Possible design response Question to verify
Join invoices to vendors by vendor_id Ensure the foreign-key path has its required supporting index. Are key types and attributes compatible?
Find one vendor's invoices by date Consider a composite index beginning with vendor_id. Does the real filter use the index's leftmost columns?
Report almost every invoice An additional index may offer little benefit. Does the query read most rows anyway?

Denormalization is a deliberate trade

Denormalization stores a controlled duplicate or derived value for a measured need. Before doing it, document the authoritative source, how copies stay synchronized, what anomaly risk is accepted, and whether query or caching changes solve the problem more safely.

MySQL 8.4 relationship note

Use compatible child and parent key types. For character keys, character set and collation must match. Design references to a PRIMARY KEY or UNIQUE NOT NULL key; MySQL's legacy support for nonunique referenced indexes is deprecated.

7. Make the design visible in a Workbench EER model

An EER model lets you review table grain, columns, keys, and relationship rules before applying DDL to a server.

  1. Open an existing model or create a new model file for the assigned schema.
  2. Add each table and write its grain in your notes before entering columns.
  3. Mark primary keys, required versus optional columns, and reasonable data types.
  4. Create relationships from the child foreign-key columns to the parent key.
  5. Read every relationship in both directions and verify cardinality and optionality against the scenario.
  6. Arrange the diagram so lines are readable, then compare the model with your written data dictionary.

A model file is not the live database

Editing an EER diagram changes the model. It does not change ap or any server until a separate implementation action is performed. In Week 3, follow the Workbench assignment's named schema and evidence steps exactly.

EER review checklist
Review question Evidence in the model
Can every row be identified?A primary or candidate key is visible.
Can an orphan child be stored?The foreign key and nullability match the business rule.
Is a many-to-many relationship unresolved?A bridge table appears with both parent references.
Does a fact appear in several homes?Dependencies and normalization have been reviewed.

8. AP design lab: place each fact where it belongs

Use this small decision lab to practice the reasoning behind the Week 3 normalization worksheet.

Which table owns the fact?

Choose a fact to reveal its determinant, grain, and destination.

vendor_phone belongs in vendors

It depends on vendor_id. Storing it on invoices or line items would repeat the same vendor fact.

invoice_due_date belongs in invoices

It describes one invoice and depends on invoice_id, not on a particular line.

line_item_amount belongs in invoice_line_items

It describes one account-coded line, identified within an invoice by its sequence.

Quick check: remove a transitive dependency

An invoice row stores vendor_id and vendor_phone. Because vendor ID determines phone, where should the phone be stored?

Does normalization guarantee a correct design?

No. Normalization helps control dependency-based redundancy, but a design can still misunderstand the business, omit a rule, choose the wrong grain, or use unclear names. Review the model with concrete scenarios and sample rows.

9. Wrap-up and practice

The core habit: write the grain before the columns

When every table has one clear row meaning, dependencies, keys, foreign keys, and normalization decisions become easier to explain and test.

Chapter 10 checklist

  • I can write “One row represents ...” for every proposed table.
  • I can identify determinants, dependent facts, and likely anomalies.
  • I can choose primary keys and place foreign keys on the child/many side.
  • I can apply 1NF, 2NF, and 3NF to a beginner business scenario.
  • I can explain why a bridge table resolves a many-to-many relationship.
  • I can select index candidates from access patterns instead of indexing everything.
  • I can review an EER model without changing the canonical ap schema.

Final quick check

Which sentence best captures second normal form for a table with a composite candidate key?
