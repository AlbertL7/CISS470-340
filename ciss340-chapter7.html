1. The question inside the question

A subquery is a complete query nested inside another SQL statement. Its result becomes an input to the surrounding query.

Analogy: ask the information desk first

Imagine that you want every package heavier than the building's average package. You first ask the information desk, “What is the average weight?” Then you take that one answer to the sorting room and compare every package with it. The information-desk question is the subquery; the sorting-room question is the outer query.

Read from the inside out

For an uncorrelated subquery, a useful mental model is to read the innermost query first. Decide what it returns, then read the outer query as though the returned value or values were placed inside it. MySQL's optimizer may choose a different physical execution plan, but this inside-out method is excellent for understanding and debugging the logic.

Scalar shape

One value

Example: one average invoice total. It fits a single-value comparison such as > or =.

List shape

One column, many rows

Example: a list of vendor IDs. It fits operators such as IN, ANY, or ALL.

Table shape

Rows and columns

Example: one summary row per vendor. It can act like a temporary table in the FROM clause.

Practice boundary

Every AP example in this chapter is read-only. Run only SELECT, WITH, DESCRIBE, or EXPLAIN statements against ap. Do not insert, update, delete, or change publisher objects.

2. One-value subqueries

A scalar subquery must return no more than one row and one column. That makes its result usable wherever SQL expects one value.

Find invoices above the overall average

AP · read-only scalar subquery 
SELECT invoice_number,
       invoice_total
FROM ap.invoices
WHERE invoice_total > (
    SELECT AVG(invoice_total)
    FROM ap.invoices
)
ORDER BY invoice_total DESC;
  1. The inner query calculates one value: the average of all invoice totals.
  2. The outer query compares each invoice total with that one value.
  3. Only rows whose total is greater than the average reach the final result.

Cardinality is the contract

If a scalar subquery returns no rows, its result is NULL. If it returns two or more rows, MySQL cannot decide which single value you meant and reports an error. Check the inner query by itself before nesting it.

A scalar subquery can filter groups in HAVING

AP · vendor averages above the overall average 
SELECT vendor_id,
       AVG(invoice_total) AS vendor_average
FROM ap.invoices
GROUP BY vendor_id
HAVING AVG(invoice_total) > (
    SELECT AVG(invoice_total)
    FROM ap.invoices
)
ORDER BY vendor_average DESC;

The outer query creates one group per vendor. HAVING then compares each group average with the one overall average returned by the subquery.

Quick check: match the shape

An inner query uses AVG(invoice_total) without GROUP BY. What shape should it return?

3. Lists with IN, ANY, and ALL

When an inner query can return several rows from one column, use an operator that understands a list. The operator expresses how the outer value should compare with that list.

Use IN for membership

AP · vendors that have an unpaid invoice 
SELECT vendor_id,
       vendor_name
FROM ap.vendors
WHERE vendor_id IN (
    SELECT vendor_id
    FROM ap.invoices
    WHERE payment_date IS NULL
)
ORDER BY vendor_name;

The inner query supplies zero, one, or many vendor IDs. IN asks whether each outer vendor ID belongs to that returned set. Duplicate IDs inside the set do not duplicate the outer vendor rows.

How the list operators read in everyday language
Operator pattern Plain-language question Typical inner shape
value IN (...) Is this value in the returned set? One column, any number of rows
value > ANY (...) Is this value greater than at least one returned value? One column, any number of rows
value > ALL (...) Is this value greater than every returned value? One column, any number of rows

SOME is a MySQL synonym for ANY. In beginner queries, use one spelling consistently so the comparison is easier to recognize.

Compare with every vendor average

AP · ALL with a list of averages 
SELECT invoice_number,
       invoice_total
FROM ap.invoices
WHERE invoice_total > ALL (
    SELECT AVG(invoice_total)
    FROM ap.invoices
    GROUP BY vendor_id
)
ORDER BY invoice_total DESC;

The inner query returns one average per vendor. The outer comparison keeps an invoice only when its total is greater than every average in that list.

NULL warning for NOT IN

If a NOT IN subquery returns even one NULL, the comparison can become unknown for every outer row. Filter NULL deliberately or, when you are asking whether a related row is missing, prefer a carefully correlated NOT EXISTS.

4. Correlated subqueries and EXISTS

A correlated subquery refers to a column from the outer query. It cannot be understood in isolation because the outer row supplies part of its input.

Analogy: a custom measuring stick

An uncorrelated subquery uses one measuring stick for everyone, such as the overall average invoice. A correlated subquery creates a measuring stick for the current group: “Is this invoice above the average for its own vendor?”

Compare each invoice with its vendor's average

AP · correlated scalar subquery 
SELECT i.vendor_id,
       i.invoice_number,
       i.invoice_total
FROM ap.invoices AS i
WHERE i.invoice_total > (
    SELECT AVG(i2.invoice_total)
    FROM ap.invoices AS i2
    WHERE i2.vendor_id = i.vendor_id
)
ORDER BY i.vendor_id,
         i.invoice_total DESC;

The reference i.vendor_id comes from the outer row. Conceptually, the inner query finds a matching vendor average for each candidate invoice. The optimizer may transform the work, so do not assume that the text is literally executed once per row.

Use EXISTS when the question is “Does a row exist?”

AP · vendors with at least one invoice 
SELECT v.vendor_id,
       v.vendor_name
FROM ap.vendors AS v
WHERE EXISTS (
    SELECT 1
    FROM ap.invoices AS i
    WHERE i.vendor_id = v.vendor_id
)
ORDER BY v.vendor_name;

EXISTS cares only whether the inner query finds a row. SELECT 1 makes that intention clear; the selected value itself is not returned to the outer query.

AP · vendors with no invoices 
SELECT v.vendor_id,
       v.vendor_name
FROM ap.vendors AS v
WHERE NOT EXISTS (
    SELECT 1
    FROM ap.invoices AS i
    WHERE i.vendor_id = v.vendor_id
)
ORDER BY v.vendor_name;

Quick check: choose the clearest tool

You need vendors for which no related invoice row exists. Which pattern states that question most directly and avoids the NOT IN/NULL trap?

5. A scalar subquery in the SELECT clause

A scalar subquery can calculate one related value for each result row. This is useful for a compact teaching example, but a join plus grouping may be clearer or more efficient for larger reports.

AP · invoice count beside each vendor 
SELECT v.vendor_id,
       v.vendor_name,
       (
           SELECT COUNT(*)
           FROM ap.invoices AS i
           WHERE i.vendor_id = v.vendor_id
       ) AS invoice_count
FROM ap.vendors AS v
ORDER BY invoice_count DESC,
         v.vendor_name;

COUNT(*) returns one number, including zero when no matching invoice rows exist. That one-value guarantee makes this subquery valid as a result column.

Name calculated columns

The alias invoice_count gives the calculated column a useful heading and lets the ORDER BY clause refer to it clearly.

6. A table subquery in the FROM clause

A subquery in FROM is often called a derived table. It creates a result with rows and columns that the outer query can filter or join.

AP · summarize first, then add vendor names 
SELECT v.vendor_name,
       va.invoice_count,
       va.average_invoice
FROM (
    SELECT vendor_id,
           COUNT(*) AS invoice_count,
           AVG(invoice_total) AS average_invoice
    FROM ap.invoices
    GROUP BY vendor_id
) AS va
JOIN ap.vendors AS v
    ON v.vendor_id = va.vendor_id
WHERE va.invoice_count >= 2
ORDER BY va.average_invoice DESC;
  1. The inner query produces one summary row per vendor.
  2. The alias va gives the derived table a required name.
  3. The outer query joins in the readable vendor name and filters the already-computed count.

Analogy: a prep table in a kitchen

The derived table is a clean prep station. One cook groups and measures the ingredients; the next cook uses that prepared result to assemble the final dish. The prep result lasts only for this statement.

7. Common table expressions

A common table expression, or CTE, gives a temporary name to a query at the start of a statement. It can make the same “build a result, then use it” logic easier to read than deeply nested parentheses.

AP · named vendor totals 
WITH vendor_totals AS (
    SELECT vendor_id,
           COUNT(*) AS invoice_count,
           SUM(invoice_total) AS invoice_total_sum
    FROM ap.invoices
    GROUP BY vendor_id
)
SELECT v.vendor_name,
       vt.invoice_count,
       vt.invoice_total_sum
FROM vendor_totals AS vt
JOIN ap.vendors AS v
    ON v.vendor_id = vt.vendor_id
ORDER BY vt.invoice_total_sum DESC;

The CTE exists only for this statement; it does not create a table in ap. Depending on the query, MySQL may merge or materialize a CTE as part of its execution plan.

What makes a recursive CTE different?

A recursive CTE refers to itself. It starts with an anchor row, then repeatedly adds rows until its stopping condition is reached. Recursive CTEs are useful for hierarchies and sequences, but they require a clear stopping rule. For this beginner module, recognizing the anchor → repeat → stop pattern is enough.

Optional recognition example · anchor, repeat, stop 
WITH RECURSIVE numbers AS (
    SELECT 1 AS n                    -- anchor

    UNION ALL

    SELECT n + 1                    -- repeat
    FROM numbers
    WHERE n < 5                     -- stop
)
SELECT n
FROM numbers;

This read-only statement returns the numbers 1 through 5. The stopping condition is essential; the goal here is to recognize the three-part structure, not to memorize a recursive exercise.

Choosing between three ways to organize an intermediate result
Pattern Where it appears Good beginner use
Scalar subquery Inside an expression Compare a row with one calculated value
Derived table Inside FROM Build a table-shaped result for one outer query
CTE After WITH Name a multi-step result so the statement reads top to bottom

8. A reliable workflow for complex questions

Long SQL becomes manageable when you treat it as several small, testable questions.

  1. Write the business question in plain language and underline words such as “average,” “any,” “every,” or “exists.”
  2. Write the smallest query that produces the needed intermediate answer.
  3. Run an uncorrelated inner query by itself and inspect its rows, columns, and possible NULL values.
  4. Match that shape to the outer operator: scalar comparison, list operator, or table expression.
  5. Add aliases and qualify shared column names so every reference has one meaning.
  6. Test the complete statement, explain its result, and compare a join or CTE version when that improves clarity.

Choice lab: start from the question

Choose a business question to see the subquery shape that fits it.

“Which invoices are above the overall average?”

Use a scalar subquery: one AVG() result paired with >.

“Which vendors appear in the unpaid-invoice list?”

Use a one-column list subquery paired with IN.

“Which vendors have no matching invoice?”

Use a correlated NOT EXISTS; the inner query tests the current outer vendor.

Must a join always replace a subquery?

No. Many questions can be written either way, and MySQL may optimize equivalent forms similarly. Choose the form whose logic you can verify and explain, then use EXPLAIN and real measurements when performance matters. A correlated EXISTS is often the clearest expression of an existence test.

9. Wrap-up and practice

The core habit: identify the returned shape

Before choosing an operator, predict whether the inner query returns one value, a one-column list, or a table. Most beginner subquery errors are shape mismatches or missing correlation conditions.

Chapter 7 checklist

  • I can describe the inner and outer query in plain language.
  • I can match scalar, list, and table results to appropriate SQL locations.
  • I can explain how an outer alias makes a subquery correlated.
  • I can use EXISTS and NOT EXISTS for related-row questions.
  • I can name a derived table and write a readable CTE.
  • I check cardinality and NULL behavior before trusting a result.
